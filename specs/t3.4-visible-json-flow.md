# T3.4 - Visible JSON Flow Specification

## Context
- T3.4 implements the visible processing flow for document capture to final JSON output.
- Requires integration of raw OCR text, T3.3 field_report, and structured output pipeline elements.
- Follows same document flow as T3.3 but exposes the processing chain visibly.
- Uses T3.2 pipeline architecture without duplicating core logic.

## Objective
Generate a structured report that demonstrates the end-to-end processing flow from documented distribution document to final JSON output by integrating:
- raw_ocr_text
- processed field candidates
- T3.3 field_report with accepted_fields, rejected_fields, missing_fields and summary_counts
- final structured JSON output meeting contract specifications

## Functional Scope
- Generic visible processing flow for all supported document types.
- Should expose processing stages without exposing internal implementation details.
- Must be reproducible with any fixture document.
- Must integrate with existing field_reporting_processor.py.

## Field Differentiation
- **raw_ocr_text**: text extracted by OCR
- **candidate_field**: potential field identified
- **validated_field**: field after semantic validation
- **rejected_field**: field rejected with reason
- **missing_field**: expected field not present
- **final_json**: structured output containing all above plus nested structure

## Expected Output Structure
The final output shall be JSON containing at minimum:
- **document_type**: generic type identifier
- **source_document_reference**: reference to input document
- **raw_ocr_text**: complete OCR output text
- **field_report** sub-object with:
  - accepted_fields: list of field identifiers
  - rejected_fields: list of field identifiers with optional reasons
  - missing_fields: list of missing field identifiers
  - summary_counts: {accepted: X, rejected: Y, missing: Z}
- **structured_output**: integration of T3.2 pipeline elements when applicable

## Acceptance Criteria for Implementation
- Visible processing chain must be executable with single command-line invocation
- Output must include all required fields in deterministic order
- No hardcoded file paths beyond input fixture directory
- No duplication of T3.2/T3.3 processing logic - must reuse existing modules
- Must work with current MVP fixture integration
- Must pass structure validation with pytest
- Must pass script validation with validate_project.py
- Must generate only final JSON structure without pipeline messages

## Expected Validations for Implementation
- pytest test suite covering success, failure, and missing scenarios
- validate_project.py validation passes
- Diff inspection shows only required changes
- Specification reviewed against this document
- Field report integration verified against T3.3 specification

## Risks
- Over-reliance on GAS pattern could introduce coupling
- Field report field names might differ between implementations
- Pipeline introspection could create performance overhead
- Feature scope creep from visible processing requirements
