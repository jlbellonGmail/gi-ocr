# T3.3 - Field Reporting Specification

## Context
- T3.3 follows T3.2 which implements controlled document to structured output pipeline.
- T3.2 generates structured output from processed documents.
- T3.3 adds auditable reporting of field classification without altering OCR or extraction logic.

## Objective
Generate a structured report classifying fields into:
- **accepted_fields**: fields that passed validation
- **rejected_fields**: fields that failed validation (with optional reason)
- **missing_fields**: expected fields that were not found

## Functional Scope
- Applies to tax invoices, service receipts, and official documents.
- Generic across document types.
- No dependency on GAS or specific provider.
- Works with fields such as: client, ticket number, date, expiration, amount, total, service, payment code, account identifier, period, document status.

## Field Differentiation
- **raw_ocr_text**: text extracted by OCR
- **candidate_field**: potential field identified
- **validated_field**: field after semantic validation
- **rejected_field**: field rejected with reason
- **missing_field**: expected field not present

## Expected Output Structure
The report shall include at minimum:
- **document_type**: generic type identifier
- **source_document_reference**: reference to input document
- **accepted_fields**: list of accepted field identifiers
- **rejected_fields**: list of rejected field identifiers (optionally with reasons)
- **missing_fields**: list of missing field identifiers
- **summary_counts**: counts of accepted, rejected, missing fields
- **validation_metadata**: schema version, validation rules used
- **execution_metadata**: timestamp of report generation

## Acceptance Criteria for Implementation
- **Successful case**: Valid fields appear in `accepted_fields`.
- **Invalid case**: Detected fields with invalid semantics appear in `rejected_fields` with documented reason.
- **Missing case**: Expected fields are listed in `missing_fields`.
- **Independence**: Report does not depend on GAS or specific provider.
- **Testability**: Report can be unit tested with pytest.
- **Reproducibility**: Output is deterministic and reproducible.

## Expected Validations for Implementation
- **pytest** test suite covering success, failure, and missing scenarios.
- **python scripts/validate_project.py** passes.
- **Diff inspection** ensures no out-of-scope changes.
- **Specification review** ensures compliance with this document.

## Risks
- Potential coupling to provider-specific field naming conventions.
- Ambiguity in field classification criteria may require future refinement.
- Specification may evolve based on implementation feedback.
